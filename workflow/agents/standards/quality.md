# 质量与验证规范

规定验证层级、开发者自验、Plan 的验证声明与完成定义。主责：Developer 执行验证，Reviewer 检查有效性，QA 独立验收。

## 1. 验证层

Plan 的「最低验证层」从下表取值，可组合，写法如 `unit + build + static`。不使用未定义的编号（如 L1、L2）。

| 取值 | 含义 | 通过证据示例 |
|---|---|---|
| `unit` | 单元测试覆盖新增或修改的逻辑路径 | 用例全部通过，含新增用例名 |
| `build` | 项目可成功编译或打包 | 构建成功日志摘要 |
| `static` | 仓库配置的 linter、类型检查、格式检查 | 零错误输出 |
| `integration` | 模块间交互、接口契约或数据流的集成验证 | 集成用例通过，或端到端命令输出 |
| `manual` | 人工验证。**仅当自动化不可行**时选用，须在 Plan 写明不可行的理由 | 逐项核对清单与结论 |

任何涉及行为变更的工作项，最低验证层至少含 `unit`；确实无法单测的，须按 `manual` 处理并写明理由。

## 2. Plan 必须声明

| 声明项 | 说明 |
|---|---|
| 最低验证层 | 取自 §1 |
| 验证命令 | 可复现的具体命令 |
| 预期证据 | 每条命令通过时的可观察输出 |

三项缺任一，Developer 不得开始实施。

## 3. 开发者自验

Developer 在交给 Reviewer 前必须执行与变更范围匹配的验证，覆盖 Plan 声明的全部层级，命令与结果记入 `dev-notes.md`。

## 4. Reviewer 检查

- **测试有效性** — 是否覆盖关键路径与边界；有无仅断言恒真的测试；能否因错误实现而失败。
- **文档影响** — 是否与 Plan 声明一致（见 [documentation.md](documentation.md)）。
- **安全影响** — 是否触发安全审阅条件（见 [security.md](security.md)）。

Review 结论须明确这三项的检查结果。

## 5. QA 独立验收

依据 Spec 与 Plan 独立验收，不得只依赖 Developer 或 Reviewer 的自述。范围含 Spec 验收条件与行为合同、Plan 的验证层与预期证据、受影响范围的回归。结论 `Pass` / `Fail` / `Blocked` 写入 `qa-report.md`。

## 6. 完成定义

| 条件 | 说明 |
|---|---|
| 实现完成 | Plan 的全部任务已实现 |
| 验证通过 | 自验与 Plan 声明的最低验证层均通过 |
| 文档更新 | Plan「文档影响」项已更新或已标 `N/A` 并写明理由 |
| Review 满足 | Review 门禁 `required` 时已 `Approve` |
| QA 通过 | 最新轮次结论为 `Pass` |
| 合并授权 | 用户已授权（非 Git 下为授权完成） |

全部满足才可置 `done`；`done` 不等待合入完成。

## 7. 无法验证时

必须记录**原因**（具体障碍）、**风险**（降级验证对质量的影响）、**恢复条件**（何时可补执行），写入 `dev-notes.md`、`qa-report.md` 或 `main.md` 的阻塞字段。

**禁止静默跳过**：未记录原因与风险的验证缺口，不得进入 QA `Pass` 或合并阶段。
