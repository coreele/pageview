# 安全规范

所有角色遵守禁止项；Reviewer 与 QA 执行安全影响检查并记录结论。

## 1. 禁止写入敏感信息

| 介质 | 示例 |
|---|---|
| 代码 | 硬编码密钥、内嵌凭据、含凭据的连接串 |
| 文档 | Spec、Plan、Review、QA 报告中的真实令牌或连接串 |
| 提交记录 | diff 或提交信息中的密钥、`.env` 内容 |
| 测试输出 | CI 日志、fixture 中的真实凭据 |
| 工作项记录 | `main.md` 中的敏感配置 |

一律使用占位符、密钥管理服务或环境变量注入；本地开发用已被 `.gitignore` 排除的 `.env`。

## 2. 安全审阅触发

变更涉及以下任一领域时，Reviewer 必须做安全影响检查，范围与变更实际影响面一致，并写进 `review.md`：

认证（登录、会话、令牌）；授权（权限模型、访问控制）；输入处理（用户输入、反序列化、注入面）；文件操作（上传下载、路径遍历）；外部网络访问（出站请求、Webhook、第三方 API）；依赖新增或升级；敏感数据（个人身份、财务、健康等受保护数据）。

## 3. 发现疑似泄露

1. **停止提交与合并**；
2. **移除暴露内容**（工作树、暂存区、已推送分支；评估是否需要重写历史）；
3. **轮换凭据**并记录轮换状态。

处置须通知 Manager，必要时把工作项置 `blocked` 直到风险消除。

## 4. 安全问题不得非阻塞放行

| 结论 | 允许放行 |
|---|---|
| `Approve` / `Pass`（问题已解决或不存在） | 是 |
| `Request changes` / `Fail`（存在未解决问题） | 否 |
| `Comment`（仅备注） | **禁止**用于安全问题 |

存在未解决安全问题时必须给出 `Request changes` 或 `Fail`，修复并复审后才能继续。

## 5. 结论记录位置

写入 `review.md`（Reviewer 检查时）或 `qa-report.md`（QA 验收时），含：检查范围、发现项、处置状态、是否允许继续合并。
