# 代码审计标准

对仓库源码做静态质量审计时的检查条款，以及须单独列出的关注项（Known Issue / Tech Debt / 优化）。

**适用：** `code-audit` skill 对照本文件及同前缀专项文件审查实现代码。

**不适用：** 工作流的验证门禁、完成定义与 Review / QA 流程——那些见 [quality.md](quality.md)，代码审计**不**依据该文件。

## 1. 结构与职责

- 模块与类型应有单一清晰职责；禁止把无关关注点堆在一起。
- 包与目录边界应反映依赖方向；禁止下层依赖上层、禁止循环依赖。
- 公开 API 面应最小；内部实现不得无必要地暴露。

## 2. 正确性与边界

- 公共方法须处理可预见的非法输入、空值与边界条件，或在合同中声明前置条件并由调用方保证。
- 错误路径须可观察：抛出有意义的错误或返回明确失败结果；禁止吞掉异常后继续在错误状态上运行。
- 共享可变状态须有明确并发约定；无约定时不得假定单线程安全。

## 3. 可读性与命名

- 命名须表达意图；禁止误导性命名与无意义缩写（惯用短名除外）。
- 控制流深度应可控；过深嵌套须拆分或提前返回。
- 注释只解释「为什么」或非显而易见的约束；禁止复述代码字面的注释，禁止保留失效注释。

## 4. 重复与复杂度

- 禁止明显可抽取的重复逻辑在多处各自漂移。
- 方法过长或分支过多须拆分为可命名的小单元，除非领域算法本身要求内聚并有注释说明。

## 5. 资源与副作用

- I/O、连接、流等资源须在所有退出路径正确关闭或移交所有权。
- 副作用（写库、写文件、出站网络）应集中在明确边界；解析与纯计算层不得隐式发起 I/O。

## 6. 依赖与可测性

- 核心逻辑应能在不启动完整外部系统的情况下被单测覆盖；对数据库、网络等边界使用接口或可替换实现。
- 测试代码不得降低生产代码的封装来迁就测试，除非有明确的测试夹具约定。
- 禁止仅恒真、不断言行为的测试冒充覆盖。

## 7. 敏感信息与配置

- 禁止在源码中硬编码密钥、令牌、生产凭据或含凭据的连接串。
- 配置与密钥须来自环境、未提交的本地配置或注入；发现疑似机密时报告位置，不在报告中回显完整值。

## 8. 关注项

除违规 Findings 外，须单独收集下列项（记为 Info / Low 或专用「关注项」表，不得与 Critical 违规混为一谈）：

| 类型 | 含义 | 须记录 |
|---|---|---|
| Known Issue | 已知缺陷或错误行为；注释、`FIXME`、`BUG` 已暗示，或逻辑上可复现但暂未修 | 位置、现象、影响面、有无临时规避 |
| Tech Debt | 能工作但拖累演进：过时 API、临时方案残留、错误抽象、缺失边界、测试缺口 | 位置、债务描述、不还清的后果、偿还方向 |
| 优化 | 非必须立刻改但值得改：性能热点迹象、API 清晰度、结构简化、重复可收敛 | 位置、现状成本、预期收益、建议优先级 |

**必须**扫描范围内的 `TODO` / `FIXME` / `HACK` / `XXX` 等标记并归类；存在 [register.md](../../audit/register.md) 时核对其条目（仍存在则更新状态，已消失则建议标 `resolved`）；每条关注项给出可执行的下一步。

**禁止**把纯风格偏好或未证实的猜测写成 Known Issue；证据不足时标「待确认」并说明缺什么证据。

## 9. 结论用法

- Finding 须可定位到文件与行（或符号），并引用本文件的章节编号。
- 关注项引用 §8 并标注类型。
- 级别：Critical（正确性或安全硬伤）、High（高概率缺陷或严重可维护性问题）、Medium（明确违规但影响局部）、Low / Info（风格、关注项、改进建议）。
- 本标准未覆盖的风格偏好不得升格为 Critical / High。

## 10. 扩展

无需修改 skill 即可扩展：

| 方式 | 约定 |
|---|---|
| 专项标准 | `workflow/agents/standards/code-audit-<topic>.md`，语言、模块、性能、并发等专项条款，与本文件一并加载 |
| 关注项登记册 | [register.md](../../audit/register.md)，持久化 Known Issue / Tech Debt / 已接受风险；是数据不是条款 |
| 用户点名 | 其他标准文件仅在用户明确指定时追加 |

专项文件结构建议：目的与适用范围（写明是补充还是收窄）→ 必须 / 禁止 / 允许条款（可检查、可定位）→ 可选的关注项示例。

**冲突：** 专项仅在其声明范围内优先，报告须注明采用了哪条；无法判断时取更严格者并说明。

**演进：** 新条款下次审计生效；对存量代码的新条款违规优先记 Tech Debt 或分阶段整改，除非属 Critical。
